# 08_BACKUP_AND_RECOVERY.md — StockLens AI

---

## 1. Backup Architecture Overview

StockLens AI's persistence layer consists of two stateful systems requiring backup:

1. **PostgreSQL** — the authoritative store for analysis run records, pipeline step metadata, metrics aggregates, and ticker resolution cache.
2. **Redis** — ephemeral operational state (rate limit counters, SSE event buffers, idempotency keys). Redis state is intentionally short-lived; Redis backup is not required for business continuity. A Redis restart returns the system to a clean state within seconds, with the only consequence being loss of in-flight pipeline events (which affect users currently waiting for analysis results).

**What is NOT backed up:**

- Redis (ephemeral by design; in-flight pipelines are lost on restart; acceptable).
- Ollama model weights (pulled from the official registry on restart; not user data).
- Next.js build artifacts (regenerated by CI on deploy).
- Prometheus metrics data (operational metrics; loss is acceptable; Prometheus TSDB can be backed up in Phase 2 if long-term metrics retention is required).

**Backup targets:**

- PostgreSQL: nightly full backup + continuous WAL archiving (Phase 2; Point-In-Time Recovery).
- Application configuration: `.env` file backed up to a separate secret store (not a file backup — managed separately).

## 5. Encryption Format

### Encryption Tool: OpenSSL AES-256-CBC

```bash
# Encrypt
openssl enc -aes-256-cbc \
  -in  stocklens_db_TIMESTAMP.sql.gz \
  -out stocklens_db_TIMESTAMP.sql.gz.enc \
  -pass env:BACKUP_ENCRYPTION_KEY \
  -pbkdf2 \
  -iter 100000 \
  -md sha256

# Decrypt
openssl enc -d -aes-256-cbc \
  -in  stocklens_db_TIMESTAMP.sql.gz.enc \
  -out stocklens_db_TIMESTAMP.sql.gz \
  -pass env:BACKUP_ENCRYPTION_KEY \
  -pbkdf2 \
  -iter 100000 \
  -md sha256
```

**Why AES-256-CBC with PBKDF2:**

- AES-256-CBC is universally supported and battle-tested.
- `-pbkdf2 -iter 100000` derives the actual encryption key from `BACKUP_ENCRYPTION_KEY` using PBKDF2-HMAC-SHA256 with 100,000 iterations. This prevents brute-force attacks if the key material is a human-memorable passphrase.
- The IV (initialization vector) is randomly generated per encryption and embedded in the file header by OpenSSL.
- The pre-encryption SHA256 is computed before encryption and stored in the manifest; the post-encryption SHA256 covers the encrypted file. Both are verified during integrity checks.

**Key management:**

- `BACKUP_ENCRYPTION_KEY` is a 256-bit randomly generated key stored in the deployment platform's secret store (Fly.io secrets, AWS Secrets Manager, or similar).
- Key rotation: a new `key_identifier` is assigned when the key is rotated. Old backups remain decryptable with their original key (both keys stored in the secret store, keyed by identifier).
- The key is NEVER stored in the backup file itself or in the manifest.

## 6. Backup Script Implementation

```bash
#!/usr/bin/env bash
# /scripts/backup.sh
# Runs inside the backup container (has pg_dump available, mounts /backups volume)

set -euo pipefail

TIMESTAMP=$(date -u +"%Y-%m-%dT%H%M%SZ")
SCHEMA_VERSION=$(psql "$DATABASE_URL" -t -c "SELECT version_num FROM alembic_version LIMIT 1" | tr -d ' ')
ENV="${ENVIRONMENT:-production}"
BACKUP_DIR="/backups/daily/${TIMESTAMP:0:10}"
BASENAME="stocklens_db_${TIMESTAMP}_v${SCHEMA_VERSION}_${ENV}"

mkdir -p "$BACKUP_DIR"

echo "[backup] Starting PostgreSQL dump..."

# 1. Dump — plain SQL format (human-readable; compatible with pg_restore and psql)
pg_dump \
  --no-owner \
  --no-privileges \
  --clean \
  --if-exists \
  --format=plain \
  --dbname="$DATABASE_URL" \
  > "${BACKUP_DIR}/${BASENAME}.sql"

# 2. Compute pre-compression, pre-encryption hash
PRE_ENCRYPT_SHA=$(sha256sum "${BACKUP_DIR}/${BASENAME}.sql" | cut -d' ' -f1)
echo "[backup] Pre-encryption SHA256: ${PRE_ENCRYPT_SHA}"

# 3. Compress
gzip -9 "${BACKUP_DIR}/${BASENAME}.sql"

# 4. Encrypt
openssl enc -aes-256-cbc \
  -in  "${BACKUP_DIR}/${BASENAME}.sql.gz" \
  -out "${BACKUP_DIR}/${BASENAME}.sql.gz.enc" \
  -pass env:BACKUP_ENCRYPTION_KEY \
  -pbkdf2 -iter 100000 -md sha256

rm "${BACKUP_DIR}/${BASENAME}.sql.gz"   # remove unencrypted compressed file

# 5. Post-encryption checksum
POST_ENCRYPT_SHA=$(sha256sum "${BACKUP_DIR}/${BASENAME}.sql.gz.enc" | cut -d' ' -f1)
echo "${POST_ENCRYPT_SHA}  ${BASENAME}.sql.gz.enc" > "${BACKUP_DIR}/${BASENAME}.sql.gz.enc.sha256"

# 6. Collect row counts for manifest
ROW_COUNTS=$(psql "$DATABASE_URL" -t -A -c "
  SELECT json_build_object(
    'analysis_runs',         (SELECT COUNT(*) FROM analysis_runs),
    'pipeline_steps',        (SELECT COUNT(*) FROM pipeline_steps),
    'system_metrics_hourly', (SELECT COUNT(*) FROM system_metrics_hourly),
    'ticker_resolution_cache',(SELECT COUNT(*) FROM ticker_resolution_cache),
    'rate_limit_log',        (SELECT COUNT(*) FROM rate_limit_log)
  )::text
")

# 7. Write manifest
COMPRESSED_BYTES=$(stat -c%s "${BACKUP_DIR}/${BASENAME}.sql.gz.enc")
EXPIRES_AT=$(date -u -d "+7 days" +"%Y-%m-%dT%H%M%SZ")

cat > "${BACKUP_DIR}/${BASENAME}.manifest.json" <<EOF
{
  "backup_id": "$(uuidgen)",
  "created_at": "${TIMESTAMP}",
  "environment": "${ENV}",
  "backup_type": "full",
  "database": {
    "schema_version": "${SCHEMA_VERSION}",
    "table_row_counts": ${ROW_COUNTS}
  },
  "files": {
    "dump_file": "${BASENAME}.sql.gz.enc",
    "dump_encrypted_bytes": ${COMPRESSED_BYTES}
  },
  "encryption": {
    "algorithm": "AES-256-CBC",
    "key_identifier": "${BACKUP_KEY_ID:-backup-key-default}",
    "iv_embedded": true
  },
  "integrity": {
    "pre_encryption_sha256": "${PRE_ENCRYPT_SHA}",
    "post_encryption_sha256": "${POST_ENCRYPT_SHA}",
    "verified_at": null
  },
  "retention": {
    "expires_at": "${EXPIRES_AT}",
    "policy": "7d-daily-4w-weekly-3m-monthly"
  }
}
EOF

echo "[backup] Backup complete: ${BASENAME}"

# 8. Sync to remote storage (S3-compatible)
if [ -n "${BACKUP_S3_BUCKET:-}" ]; then
  aws s3 sync "${BACKUP_DIR}" "s3://${BACKUP_S3_BUCKET}/daily/${TIMESTAMP:0:10}/" \
    --storage-class STANDARD_IA \
    --sse AES256
  echo "[backup] Synced to S3: s3://${BACKUP_S3_BUCKET}/daily/${TIMESTAMP:0:10}/"
fi
```

## 7. Integrity Verification

Integrity verification runs daily at 03:00 UTC (1 hour after backup) as a separate cron job. It verifies the most recent backup and a randomly selected backup from the past 7 days.

```bash
#!/usr/bin/env bash
# /scripts/verify_backup.sh

set -euo pipefail

BACKUP_FILE="$1"     # path to .sql.gz.enc
MANIFEST_FILE="$2"   # path to .manifest.json

echo "[verify] Starting integrity check for: $BACKUP_FILE"

# 1. Verify post-encryption checksum
ACTUAL_SHA=$(sha256sum "$BACKUP_FILE" | cut -d' ' -f1)
EXPECTED_SHA=$(jq -r '.integrity.post_encryption_sha256' "$MANIFEST_FILE")

if [ "$ACTUAL_SHA" != "$EXPECTED_SHA" ]; then
  echo "[verify] FAILED: Checksum mismatch. File may be corrupted."
  echo "[verify] Expected: $EXPECTED_SHA"
  echo "[verify] Actual:   $ACTUAL_SHA"
  exit 1
fi
echo "[verify] Checksum OK"

# 2. Test decryption (without writing full output to disk)
openssl enc -d -aes-256-cbc \
  -in "$BACKUP_FILE" \
  -pass env:BACKUP_ENCRYPTION_KEY \
  -pbkdf2 -iter 100000 -md sha256 | \
  gzip -d | \
  head -c 1024 > /dev/null   # read first 1KB to confirm decryptability

if [ $? -ne 0 ]; then
  echo "[verify] FAILED: Decryption test failed. Key may be incorrect."
  exit 1
fi
echo "[verify] Decryption test OK"

# 3. Verify pre-encryption hash by full decrypt + hash
TEMP_FILE=$(mktemp)
openssl enc -d -aes-256-cbc \
  -in "$BACKUP_FILE" \
  -pass env:BACKUP_ENCRYPTION_KEY \
  -pbkdf2 -iter 100000 -md sha256 | \
  gzip -d > "$TEMP_FILE"

ACTUAL_PRE_SHA=$(sha256sum "$TEMP_FILE" | cut -d' ' -f1)
EXPECTED_PRE_SHA=$(jq -r '.integrity.pre_encryption_sha256' "$MANIFEST_FILE")
rm "$TEMP_FILE"

if [ "$ACTUAL_PRE_SHA" != "$EXPECTED_PRE_SHA" ]; then
  echo "[verify] FAILED: Pre-encryption hash mismatch. Backup content may be corrupted."
  exit 1
fi
echo "[verify] Pre-encryption hash OK"

# 4. Update manifest with verification timestamp
jq --arg ts "$(date -u +"%Y-%m-%dT%H%M%SZ")" \
  '.integrity.verified_at = $ts' \
  "$MANIFEST_FILE" > "${MANIFEST_FILE}.tmp" && mv "${MANIFEST_FILE}.tmp" "$MANIFEST_FILE"

echo "[verify] Integrity check PASSED: $BACKUP_FILE"
```

## 8. Restore Procedure

### 8.1 Full Restore (Disaster Recovery)

**Preconditions:**

- Target PostgreSQL instance is running (fresh or same instance after data loss).
- `BACKUP_ENCRYPTION_KEY` environment variable is set to the key matching the backup's `key_identifier`.
- Alembic migration scripts are available at the current codebase's `db/versions/`.

**Step-by-step restore:**

```bash
#!/usr/bin/env bash
# /scripts/restore.sh

set -euo pipefail

BACKUP_FILE="$1"     # path to .sql.gz.enc
TARGET_DB_URL="$2"   # postgresql://user:pass@host:5432/dbname

# 1. Verify integrity before restore
./verify_backup.sh "$BACKUP_FILE" "${BACKUP_FILE%.sql.gz.enc}.manifest.json"

# 2. Decrypt and decompress to temp file
TEMP_SQL=$(mktemp --suffix=.sql)
echo "[restore] Decrypting and decompressing backup..."

openssl enc -d -aes-256-cbc \
  -in "$BACKUP_FILE" \
  -pass env:BACKUP_ENCRYPTION_KEY \
  -pbkdf2 -iter 100000 -md sha256 | \
  gzip -d > "$TEMP_SQL"

# 3. Drop and recreate the database (clean slate)
echo "[restore] WARNING: This will DESTROY all existing data in the target database."
read -p "Type 'CONFIRM' to proceed: " confirmation
if [ "$confirmation" != "CONFIRM" ]; then
  echo "[restore] Aborted."
  rm "$TEMP_SQL"
  exit 1
fi

psql "${TARGET_DB_URL%/*}/postgres" -c "DROP DATABASE IF EXISTS stocklens;"
psql "${TARGET_DB_URL%/*}/postgres" -c "CREATE DATABASE stocklens;"

# 4. Restore SQL dump
echo "[restore] Restoring database..."
psql "$TARGET_DB_URL" < "$TEMP_SQL"
rm "$TEMP_SQL"

# 5. Run forward migrations if backup schema version < current head
BACKUP_SCHEMA=$(jq -r '.database.schema_version' "${BACKUP_FILE%.sql.gz.enc}.manifest.json")
echo "[restore] Backup schema version: ${BACKUP_SCHEMA}"
echo "[restore] Running Alembic migrations to current head..."
cd /app && alembic upgrade head

# 6. Validate restore
echo "[restore] Validating restored data..."
psql "$TARGET_DB_URL" -c "SELECT COUNT(*) AS run_count FROM analysis_runs;"
psql "$TARGET_DB_URL" -c "SELECT version_num FROM alembic_version;"

echo "[restore] Restore complete."
```

### 8.2 Restore Validation Logic

After restore, the following assertions are checked automatically:

```python
# validate_restore.py — run after restore script completes
async def validate_restore(pool: asyncpg.Pool, manifest: dict):
    """
    Validates a restored database against the backup manifest.
    Raises AssertionError if any validation fails.
    """
    async with pool.acquire() as conn:
        # 1. Alembic version matches (or is ahead due to forward migration)
        version = await conn.fetchval("SELECT version_num FROM alembic_version")
        assert version is not None, "Alembic version table missing"

        # 2. Table row counts are within 5% of manifest values
        # (some rows may have been created/deleted between backup and restore)
        expected_counts = manifest["database"]["table_row_counts"]
        for table, expected in expected_counts.items():
            actual = await conn.fetchval(f"SELECT COUNT(*) FROM {table}")
            if expected > 0:
                ratio = actual / expected
                assert 0.95 <= ratio <= 1.05, (
                    f"Row count mismatch for {table}: "
                    f"expected ~{expected}, got {actual}"
                )

        # 3. No orphaned pipeline_steps (FK integrity)
        orphans = await conn.fetchval("""
            SELECT COUNT(*) FROM pipeline_steps ps
            WHERE NOT EXISTS (
                SELECT 1 FROM analysis_runs ar WHERE ar.run_id = ps.run_id
            )
        """)
        assert orphans == 0, f"Found {orphans} orphaned pipeline_steps rows"

        # 4. No runs stuck in 'in_progress' (they were in-flight at backup time;
        #    all in-progress runs are set to 'failed' post-restore)
        await conn.execute("""
            UPDATE analysis_runs
            SET status = 'failed',
                error_message = 'Run was in-progress at backup time; marked failed on restore'
            WHERE status IN ('accepted', 'in_progress')
        """)

        print("Restore validation PASSED")
```

## 9. Partial Restore Strategy

### 9.1 When Partial Restore Is Needed

A partial restore is used when:

- A specific analysis run was accidentally deleted and a user has requested it via the API.
- A specific table is corrupted but others are intact.
- A debugging session requires inspecting historical run data without affecting the live database.

### 9.2 Restore to Separate Schema

Partial restore is performed by restoring the backup dump into a separate PostgreSQL schema (not the main `public` schema), then extracting the required rows:

```bash
# Create isolated restore schema
psql "$TARGET_DB_URL" -c "CREATE SCHEMA restore_20250311;"

# Restore dump into isolated schema (using search_path override)
psql "$TARGET_DB_URL" -c "SET search_path TO restore_20250311;" < decrypted_dump.sql

# Extract specific run
psql "$TARGET_DB_URL" -c "
  INSERT INTO public.analysis_runs
  SELECT * FROM restore_20250311.analysis_runs
  WHERE run_id = 'target-uuid-here'
  ON CONFLICT (run_id) DO NOTHING;
"

# Clean up restore schema
psql "$TARGET_DB_URL" -c "DROP SCHEMA restore_20250311 CASCADE;"
```

### 9.3 Point-in-Time Recovery (Phase 2)

Phase 1 uses nightly dumps only. Phase 2 adds PostgreSQL WAL archiving for PITR:

```
# postgresql.conf additions (Phase 2)
wal_level = replica
archive_mode = on
archive_command = 'aws s3 cp %p s3://stocklens-wal-archive/%f'
```

With WAL archiving, recovery is possible to any point between the last full backup and the last archived WAL segment — enabling recovery to within seconds of a data loss event.

## 10. Compatibility with Schema Migrations

### The Core Problem

A backup taken at schema version `v0005` must be restorable even if the current codebase is at `v0008`. The backup dump contains the schema as it was at `v0005`; the application expects `v0008`.

### Resolution

1. The restore script applies the backup dump first (restoring schema at `v0005`).
2. The restore script then runs `alembic upgrade head`, which applies migrations `v0006`, `v0007`, and `v0008` sequentially.
3. Each migration is reversible (`downgrade()` is implemented), so if a migration fails during restore, `alembic downgrade -1` is safe to use.

### Migration Constraint for Backup Compatibility

All Alembic migrations must follow these rules to maintain backup compatibility:

1. **Never drop a column in a single migration.** Use the two-migration pattern: first add the new column (nullable or with default), deploy, then drop the old column in a subsequent migration. This ensures a backup taken between the two migrations can always be migrated forward.

2. **Never rename a column.** Use add + backfill + drop. Renaming a column in the dump's schema makes the dump incompatible with migrations that reference the old column name.

3. **New NOT NULL columns must have defaults.** A migration that adds `ALTER TABLE ... ADD COLUMN new_col VARCHAR NOT NULL` without a default will fail when applied to a restored dump that doesn't have the column (the existing rows will violate the constraint). Always add columns with `DEFAULT ''` or equivalent, then remove the default constraint separately after backfill.

4. **Data migrations are idempotent.** Any migration that modifies data (UPDATE statements) must be safe to re-run on data that already had the migration applied. Use `WHERE ... IS NULL` or `WHERE ... = 'old_value'` conditions.

## 11. Scheduled Backup Mechanisms

### Container-Based Scheduling

The backup container uses a `cron` daemon to schedule backup and verification jobs:

```
# /etc/cron.d/stocklens-backup
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/sbin:/bin:/usr/sbin:/usr/bin

# Daily full backup at 02:00 UTC
0 2 * * * root /scripts/backup.sh >> /var/log/backup.log 2>&1

# Daily integrity verification at 03:00 UTC
0 3 * * * root /scripts/verify_latest_backup.sh >> /var/log/backup-verify.log 2>&1

# Weekly backup promotion (copy daily to weekly on Sunday)
0 4 * * 0 root /scripts/promote_weekly_backup.sh >> /var/log/backup-promote.log 2>&1

# Monthly backup promotion (first day of month)
0 5 1 * * root /scripts/promote_monthly_backup.sh >> /var/log/backup-promote.log 2>&1

# Retention cleanup (delete expired backups)
0 6 * * * root /scripts/cleanup_expired_backups.sh >> /var/log/backup-cleanup.log 2>&1
```

### Backup Container in Docker Compose

```yaml
# docker-compose.yml excerpt
backup:
  image: stocklens/backup:latest
  environment:
    - DATABASE_URL=${DATABASE_URL}
    - BACKUP_ENCRYPTION_KEY=${BACKUP_ENCRYPTION_KEY}
    - BACKUP_KEY_ID=${BACKUP_KEY_ID}
    - BACKUP_S3_BUCKET=${BACKUP_S3_BUCKET}
    - ENVIRONMENT=production

    - backup_data:/backups
    - ./scripts:/scripts:ro

    - db

    - stocklens_internal

  backup_data:
    driver: local
```

### Backup Failure Alerting

If the backup script exits with a non-zero code, the cron daemon writes to `/var/log/backup.log`. A Promtail rule ships this log to Loki. A Grafana alert fires if:

- No backup log entry with "Backup complete" appears within a 26-hour window (catches a missed backup).
- Any backup log entry contains "FAILED".

The alert sends a notification via the configured alerting channel (email or webhook).

## 12. Recovery Time and Recovery Point Objectives

| Scenario | RPO | RTO | Recovery Method |
|---|---|---|---|
| Database corruption (MVP) | ≤ 24 hours | ≤ 2 hours | Full restore from latest daily backup |
| Accidental table drop (MVP) | ≤ 24 hours | ≤ 1 hour | Partial restore to separate schema |
| Accidental row deletion (MVP) | ≤ 24 hours | ≤ 30 min | Partial restore, targeted row extraction |
| Database corruption (Phase 2, WAL) | ≤ 5 minutes | ≤ 2 hours | PITR from WAL archives |
| Application container crash | 0 (stateless) | ≤ 2 minutes | Docker restart policy |
| Redis crash | 0 (ephemeral) | ≤ 30 seconds | Docker restart policy; in-flight pipelines lost |
| Host failure | ≤ 24 hours | ≤ 4 hours | Provision new host, restore from backup, re-deploy |

**Note on in-flight pipeline loss on Redis crash:** When Redis restarts, all SSE event buffers, idempotency keys, and rate limit counters are lost. Users whose analysis was in-progress at the time of the crash will see a stalled SSE stream. Their browser will eventually error out (SSE connection dropped). They will need to resubmit their ticker. This is an explicitly accepted trade-off given the 24-hour run retention in PostgreSQL means completed runs are still retrievable.
